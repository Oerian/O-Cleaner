## 阶段 0：环境校准（先做，否则后面全白做）

1. `git -C E:\O-Cleaner log --oneline -3` 与 `git status` 确认基线；工作区应为干净。
2. **服务器重启铁律**：改动任何 `.py` 后必须杀掉旧进程再起新进程（`netstat -ano | grep 8770` 找 PID → Stop-Process → 重启 → 用 `Get-Process -Id <pid> | Select StartTime` 核验是刚起的）。Python 代码是进程启动时导入的，旧进程 + 新 JSON 会产生「半新」假象，历史上坑过两次。
3. 常驻坑位清单（都在交接文档与记忆里，别重复排查）：
   - cdp_check.js 必须显式传 `http://127.0.0.1:8770`（默认 8797 会让所有 evaluate 抛 Uncaught）；
   - 本机完整 `selftest.py` 因宿主删除配额跑不完，阶段二 Temp 沙箱处必卡——**完整套件权威验证走 CI**，本机只跑 `lint_rules.py --strict`、`_lint_selftest.py`、pyflakes、CDP；
   - Bash 工具 CWD 会静默重置，一律 `git -C` + 绝对路径；管道取退出码必须 `out=$(cmd 2>&1); rc=$?`；
   - `gh` 在 `C:\Program Files\GitHub CLI\gh.exe`（全路径调用）；push 优先 SSH（晚高峰 HTTPS 被按 IP 阻断）；
   - 所有临时文件、探针脚本放 `$TEMP` 或仓库 gitignore 目录，**绝不落任何盘根**。

## 阶段 2：功能测试（E2E）

起服务器后逐项过（每项都真实调用，不凭代码推断）：

1. **核心链路**：`/state`、`/scan`、`/overview`（快扫 + 全盘两档）、`/subdirs` 下钻、`/clean`（用 `$TEMP` 下自造的垃圾目录，**真实清理走回收站**）、`/progress` 轮询。
2. **专项功能**：回收站精确清空（`recycle-purge`，验证只删配对项）、被占用文件探测（`locks`）、游戏发现（Steam/Epic/GOG，无样本机则走合成清单断言）、大文件排行（`bigfiles`）、检查更新、清理回执落盘。
3. **自定义数据四件套**：命名规则、自定义释义覆盖、资源包导入/启停/更新（远端 `Oerian/O-Cleaner-packs`）、**自定义聚合组**（`fsgroups`：add/remove/rename/delete + `.bak` 备份 + 重启后保留）。
4. **AI 通道**（若 `config/ai.json` 有 Key）：explain / plan，验证「AI 只能建议不能删」护栏。
5. **i18n**：`?lang=zh` 与 `?lang=en` 全页面切换，重点看动态文案（自动发现标签、风险徽章「无/None」、细分合计卡两形态、缓存命中提示）。
6. **门禁**：`fix-encoding.ps1 -Check`（pwsh 全路径）、`lint_rules.py --strict`、`_lint_selftest.py`（44/0 预期）、`cdp_check.js http://127.0.0.1:8770`（失败 0 即绿；跳过是环境说明）。
7. 记录每项：通过 / 失败（附最小复现）/ 无法本机验证（说明原因）。**把失败归因环境之前，先问「CI 上能不能复现」**——历史上把真缺陷当环境问题豁免过。

## 阶段 3：压力测试（找边界崩坏，别怕搞崩）

用脚本自造数据（全放 `$TEMP`），每项记录：表现、耗时量级、是否优雅降级：

1. **超大目录树**：5 万+ 小文件的扁平目录、100 层深嵌套、超长路径（>260 字符）、中文/emoji/空格文件名——分别测扫描、下钻、清理勾选。
2. **极端尺寸**：0 字节文件/目录撑起的目标、单目录 10 万条目（追加式分页是否还活）、`history.json` / `disk-trend.json` 人为灌 5000 条后趋势图与 stats 性能。
3. **并发**：扫描进行中并发 `/clean`、并发 `/subdirs` 下钻、并发 fsgroups 写操作——找竞态与状态串扰（此前修过「换盘后旧盘在途响应覆盖新盘」）。
4. **恶意/畸形输入**（只打 API，不真删）：`E:`、`..\Windows`、`/etc`、空路径、超长参数、非 JSON body、未知 op——预期全部被 400/护栏拒绝，任何一条被 `abspath` 解析到仓库自身即 P0。
5. **WizTree 边界**：CSV 含异常行（引号数字、缺尾反斜杠、超深路径）时解析器是否丢行不崩。

## 阶段 4：项目分析（观点要给出处，不许空泛）

1. **继续与否**：项目当前完成度、剩余缺陷密度（用阶段 1–3 的实测数据说话）、维护成本 vs 价值的趋势判断——给出「继续 / 收敛维护 / 归档」三选一及理由。
2. **可替代性**：逐项对比同类工具——WizTree（本体的扫描速度是否已覆盖本项目加速层）、CCleaner、BleachBit、TreeSize、SpaceSniffer、Windows 内置「存储感知」。指出哪些能力**只有** O-Cleaner 有（如：本地 AI 解释、自定义聚合组、资源包生态、零依赖便携、中文名游戏库），哪些是「能用但同类更好」。诚实评估：如果同类工具 + 两行 PowerShell 就能替代 80% 场景，直说。
3. **创新性**：真实亮点排序（建议候选：单文件零依赖、MFT 加速 + 原生回退双引擎、安全护栏体系、packs 生态、AI 接入的「建议不删除」边界）与抄袭风险/同质化风险。
4. **定位**：一句话——它本质是「个人向空间治理台」还是「可分发产品」？用户当前偏好是自用 + 公开源码，这决定后面所有优先级。

## 阶段 5：规划与优化方向设计

1. **缺陷修复清单**：按 P0（安全/数据丢失风险）→ P1（功能坏）→ P2（体验）排序，每条附阶段 1–3 的证据。
2. **优化方向**：性能（无 WizTree 回退路径、前端渲染 10 万节点）、架构（app.py 已 312KB，下一步拆什么）、测试（CI 覆盖 vs 本机受限的长期解法）。
3. **路线图**：短期（下个版本）应含「推送 15 个待推提交 + 重建发布包」这一既定动作；中期 3 项以内；长期方向与阶段 4 结论对齐。**每项给优先级理由，不列愿望清单。**
4. 明确「不建议做」清单：与项目约束冲突的方向（引入 pip/npm 依赖、打包 WizTree 二进制、放宽 cleanable 判据换召回），说明为什么。
