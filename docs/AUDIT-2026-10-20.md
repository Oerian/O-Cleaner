## 三、发现并已修复的缺陷（4 个本地提交）

### P1-1：`clean` 回收站通道 `only_paths` 无校验即可删除任意路径（`24a24ec`）
- 证据：`clean_target()` 的 `kind=="recyclebin"` 分支对请求体里的 `only_paths` 逐条直接 `rm()`，不经过 `check_deletable`，也不验证位于 `$Recycle.Bin` 内。同信任边界下其它通道全部做了服务端二次校验，此处是防线缺口（端口仅绑 127.0.0.1 + CSRF 校验是唯一屏障）。
- 修复：逐条校验归一化路径必须位于目标对应盘 `$Recycle.Bin\` 之下，否则计入 `failed` 并带原因返回。
- 验证：进程内注入 `E:\O-Cleaner\HANDOFF.md` 请求 → 拒绝且文件健在。

### P1-2：junction / 符号链接可绕过整条保护链（`d3cc4db`）
- 证据：`check_deletable` 全部规则基于路径**字符串分段名**；指向 `C:\Windows` 的 junction（如 `D:\cache-link`）段名自选、不命中任何名单，且 Windows 上 Python `islink()` 对 junction 返回 False，`shutil.rmtree` 会穿过它删真实目标。
- 修复：对真实存在的目标 `os.path.realpath` 解析，解析结果与原路径不一致时对真实路径**重新执行同一套检查**（只会更严，符合「宁可少推荐」取向）。同时新增仓库自身（`BASE_DIR`）硬保护。
- 验证：进程内建 junction → `C:\Windows` 被拒（「Windows 属于受保护的系统目录」）；仓库目录/文件被拒；正常目录不受影响。

### P2-1：`bigfiles` 与 `schedule` 参数非数字 → 500（`303e785`）
- 实锤复现：`limit="abc"`、`interval_hours:"abc"` 均 500。修复为 400，与 `/subdirs` 的 limit 校验同口径。

### P2-2：前端 `.warnpane` 规则括号错位 + `normOvKey` 契约漂移（`e30e6f0`）
- `.warnpane{...` 缺右括号被下一规则打断，`.warnpane.warm`（实际在用）样式失效；
- `normOvKey` 双重定义（3013 行别名版 / 3403 行内联版），内联版少做 `/→\` 全量替换，违反「归一化契约只此 normKey 一份」。已删除内联版（调用方由别名版承接）。

## 二、修复策略要点

- **P0 双保险 + 可选化**：第一层按**名字**（`USER_DATA_DIR_NAMES`：documents / desktop / downloads / pictures / videos / music / favorites / saved games / my-* / 3d objects），第二层按**位置**（`C:\Users\<用户名>\` 的一级子目录），两层都遵循「**默认不删、显式可选**」。

  产品口径（2026-10-21 用户确认）：**不做删，做成可选**。
  - 默认（`allow_user_data=False`）：拒绝。预设、自动发现、定时清理、规则清理**全部**走默认值 —— 那些调用点根本不传参数，所以「工具永不主动碰个人数据」是代码结构保证的，不靠调用方自觉。
  - 显式（`allow_user_data=True`）：放行。只由 `/clean` 在用户勾选了「建议保留 / 未识别项」时传入，等价于用户亲手选中。

  系统目录（Windows / System32 / Program Files）、工具自身、盘根、junction 真实路径、8.3 短名这些**不受该开关影响** —— 删了系统就坏了，不该由一次误点决定。

  为什么还要保留「按位置」这一层：名字名单永远列不全。中文系统的「文档/桌面/下载」在磁盘上可能被 OneDrive 重定向成中文目录名，用户也可能自建「工作资料」这类一级目录。只按名字漏判，只按位置则会把 `AppData\Local\Temp` 这类缓存目录一起挡死，所以两层都要。
- **P1 调度**：`next_run` 推进移到 `finally`；`_schedule_run_interval()` 把值钳到 [0.25h, 720h]，非法值回落 24h 且**绝不抛异常**；未知预设返回空集并写可读原因，不再静默跑空。
- **P1 并发**：`_atomic_write` 临时文件名带 `pid + tid + uuid8`，并加 4 次短重试（Windows 上 `os.replace` 会被杀软/索引器短暂占用）。
- **P2 探针**：`data_dir_writable` 进程内只探一次并缓存，并 `except SystemExit`（宿主的删除保护钩子抛的是 `SystemExit`，不是 `Exception` 子类，`except OSError` 拦不住）。

# 第四轮：护栏升级（v2.8，2026-10-21）

> 指令：「升级护栏，然后进行一次版本推送」。方法：先用探查脚本把「明显不该删」的路径逐个问 `check_deletable`，**按真实漏判决定改什么**，而不是凭印象加名单。

## 一、探查发现的真实缺口

对 25 个高危路径逐个取判定（`exists=True` 且默认放行的才算缺口）：

| 路径 | 升级前 | 危险在哪 |
|---|---|---|
| `Users\<u>\AppData\Roaming` | **默认放行** | 所有程序的配置与登录状态的家 |
| `Users\<u>\AppData\Local` | **默认放行** | 所有程序的本地数据 |
| `Users\<u>\AppData\LocalLow` | **默认放行** | 低完整性进程（IE/沙箱）数据 |
| `Users\<u>\AppData\Local\Packages` | **默认放行** | UWP 应用数据，删了应用即失联 |
| `Users\<u>\AppData\Roaming\Microsoft` | **默认放行** | 开始菜单、输入法、Office 设置 |

| `Program Files\WindowsApps` | **默认放行** | 商店应用本体 |
| **`Users\<u>\Documents\Adobe`** | **默认放行** | ← 这就是第三轮真实事故的路径 |

最后一条是本轮最关键的发现：名字规则保护 `Documents` 本身，位置规则只管 `Users\<u>\` 一级，**而用户在下钻后勾的正是 `Documents\Adobe` 这一层**。也就是说第三轮的「默认不删」只保住了树根，子树是敞开的。

## 二、改法（4 个提交）

1. **受保护域 + 子树继承**（`_guarded_zone`）：`Users\<u>\*`、`AppData\<Local|Roaming|LocalLow>\*`、`ProgramData\*`、`Program Files[ (x86)]\*` 四棵子树的整目录删除一律默认拒绝，需 `allow_user_data=True`。豁免 `ZONE_CACHE_EXEMPT`（Temp/Cache/Logs/Code Cache/GPUCache/ShaderCache/INetCache/DXCache/D3DSCache/Explorer/WER…），这些是删了自动重建的派生数据。
2. **显式选择强制回收站**：`allow_user_data=True` 的目标 `trash` 强改为真，用户关掉「高风险项进回收站」也绕不过去。理由：「可选」这一档的意义就是可后悔。
3. **名单补强**：`Common Files`、`WindowsApps` 进「绝不删」。
4. **保留设备名**：`CON`/`PRN`/`AUX`/`NUL`/`COM1-9`/`LPT1-9` 一律拒绝（Win32 层是设备不是文件）。

## 三、误伤检查（这一步不能省）

护栏「只增不减」很容易把产品自己的功能锁死。用 `build_targets` 对 C/D/E 三盘枚举全部 47 个清理目标，逐个问 `check_deletable`：

## 四、门禁

# 第五轮：收尾修复（v2.9，2026-10-21）

> 指令：「继续修」。目标是清掉 v2.8 报告里记录在案的遗留，外加把本机自测一直红着的三项搞清楚。

## 一、`drive-part-files` 目标恢复可用

`%DRIVE%` 展开成 `C:`（盘符相对路径），被「必须是绝对路径」拦死 —— 这个目标从 v2.7 起就是坏的，勾选只会得到一条错误。

**修法分两处，关键是「窄口开在哪」**：

| 改法 | 理由 |
|---|---|
| 目标 path 改成 `%DRIVE%\` | 展开后是 `C:\`，`os.scandir` 语义明确，不再依赖 per-drive CWD |
| 窄口写在 `clean_target`，**不写进 `check_deletable`** | 后者看不到 glob。一旦让它认盘根，任何调用方（含第三方资源包）都能用 `glob=*` 清盘根 |

放行条件是三重收窄：`kind="files"`（删除循环只处理顶层匹配文件，不递归、不删目录）＋ 路径正好是盘根 ＋ `drive_root_glob_ok()`（只接受 `*.ext`，`*` / `*.*` / `**` / `*.part*` 全拒）。

验证：E 盘根放 `.part` + `.txt` 各一个 → `.part` 被删（1 个文件 2048 B）、`.txt` 保留；glob 换成 `*` 仍拒绝；`kind=tree` 仍拒绝。门禁加 F 组 + 规则单元自检，缺陷注入（窄口恒真）→ rc=1。

## 二、浏览器资料目录判定误伤（真缺陷）

本机自测里「名字像浏览器但缺资料目录结构时不误判（E:\Chrome）」一直红。查下来 `E:\Chrome` 是个 AI 工具合集，但 `sd-webui-*\extensions` 命中了 `extensions` 这个「强特征」—— 而 `extensions` / `history` / `preferences` / `bookmarks` / `service worker` **根本不是浏览器专有**（SD WebUI 有 extensions，几乎任何开发项目都可能有 history）。

**改法**：把特征分两级。
- `core`（只有浏览器有）：`user data` / `local storage` / `indexeddb` / `session storage` / `web data` / `login data` —— 命中任意一个即认定。
- `aux`（浏览器有、别处也常见）：`service worker` / `extensions` / `bookmarks` / `preferences` / `history` —— **必须凑够两个**才算证据。

改后：`E:\Chrome` → 「未识别」且 `cleanable=False`（不会建议删除）；本机真实的 Chrome / Edge `User Data\Default` 仍正常认出（它们有 Local Storage / IndexedDB）。

## 三、两条一直红着的自测断言

| 断言 | 真相 | 处置 |
|---|---|---|
| 「被标游戏本体的节点不可清理」 | 与两行外的代码**相反**（代码明确 `cleanable=True`、`risk=高`，游戏本体按整款删除） | 断言写错了，改成「按整款删除处理：类别=游戏 + 风险=高 + 可清理」。它自 v2.2 起就是红的，只因只在装了 Epic 游戏的机器上才跑，一直没暴露 |
| 阶段七 `PermissionError: D:\_oc_pin_probe` | 该机器 D 盘根不可写（ACL/组策略），`os.makedirs` 抛异常把整个阶段带崩 | 环境不具备 → 记「跳过」而不是失败（提级验的是显示偏好，与磁盘权限无关） |
