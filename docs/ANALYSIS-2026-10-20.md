# O-Cleaner 项目分析报告（2026-10-20）

> 依据：2026-10-20 全量审计（见 AUDIT-2026-10-20.md）+ HANDOFF v2.8 需求追溯 + 同类工具横向对比。

## 一、继续与否：**收敛维护**（三选一结论）

- **完成度**：REQ-01 ~ REQ-20 全部需求已落地，HANDOFF 自述「无既定未完项」，本次独立审计未发现功能级缺失。
- **缺陷密度（实测）**：全量静态 + E2E + 压测仅出 2 P1 + 4 P2（当日全部修复/记录），门禁与 CDP 全绿。以单维护者项目衡量，这个密度很低。
- **成本趋势**：`app.py` 已 318KB / ~6700 行，单文件维护成本持续上升；i18n、fsgroups、packs、AI 等子系统均已稳定，边际功能收益递减。
- **判断**：项目处于「功能平台期」。继续大规模加功能性价比低；归档则浪费一个已打磨到位、有真实差异化价值的工具。**收敛维护**——修缺陷、跟 Windows/Steam 格式变动、小步优化，是当前最优解。

## 一·补充（第二轮复核，2026-10-21）

第二轮换视角重做审计后，上面的「收敛维护」结论**不变，但优先级要调整**：安全性修复必须排在收敛之前。

- **缺陷密度需要修正判断**：第一轮报「2 P1 + 4 P2，密度很低」，但第二轮用对抗测试（而不是罗列式审查）又挖出 **1 个 P0 + 2 个 P1 + 5 个 P2**。说明第一轮的「密度低」是**测试方法不够对抗**造成的，不是代码真的干净。对清理工具而言，「常规测试通过」和「护栏真的拦得住」是两件事 —— 前者的结论不能替代后者。
- **P0 的含义**：`check_deletable` 放行 `Documents`/`Desktop`/`Downloads` 这类用户数据目录，且 `clean_target` 确实把它们删掉了（`freed=14336, deleted=3`）。这不是「体验不好」，是**数据丢失风险**。一个清理工具的护栏漏判，比它少扫几个目录严重一个量级。
- **P1 已在真实运行中造成事故**：定时清理的 `next_run` 不推进，导致 2 分钟内连续 6 次真实清理（最大一次 freed 8.9 GB）。这类缺陷只有真的把调度线程跑起来才会暴露 —— 静态读代码看不出来。
- **结论修正**：项目仍然值得**收敛维护**，但「收敛」的定义要加一条 —— **先做一轮以「护栏正确性」为目标的对抗性验证**，再做功能收敛。当前自动化门禁（85 项 CDP + 44 项 lint selftest）覆盖的是「界面能跑通」，**不覆盖「护栏边界是否正确」**。这是本项目质量体系当前最大的结构性缺口，建议补一个 `tools/guard_matrix.py` 把本轮 25 项护栏矩阵固化进门禁（见 ROADMAP）。

## 一·补充二（第三轮：口径变更 + 清零，2026-10-21）

用户给了明确口径：**「不做删，做成可选就可以，开始修复所有已知问题」**。这改变了第二轮的 P0 处置方式，也把「收敛维护」的下一步从「加门禁」变成了「加门禁 + 一次清完」。

### 3.1 一个重要的判断修正：P0 的正确解法不是「更严」，而是「不替用户做决定」

第二轮把「`check_deletable` 放行用户数据目录」定为 P0，当时的直觉解法是把护栏收紧、把这些目录永久拉黑。但用户口径给出了更好的答案：**默认不删 + 显式可选**。

- **为什么这比「永久拉黑」更好**：永久拉黑是产品替用户判断「你的 Documents 不能删」。但用户可能确实有一个 300 GB 的 `Downloads` 想整体清掉——这时工具的正确姿态是「我说清楚风险，你自己确认」，而不是「我不允许」。
- **为什么这比「直接放行」安全**：删整目录是不可逆的高风险动作，不能和清缓存混在同一个勾选流里。所以「可选」必须带三条约束——**不进推荐、不进预设、不被 `selectAll` 勾中**。用户必须主动找到它、主动勾它、主动确认。
- **落到代码上**：名单拆成「绝不删」与「默认不删」两级，判断函数加 `allow_user_data` 开关，结果落 `user_data_optin: true` 到历史记录里，事后能查清「这次是用户自己勾的」。
- **关键约束没松动**：`C:\Windows` / `Program Files` / 仓库自身 / 盘根 / junction 指向系统目录，**显式勾选也一律拒绝**。门禁里 D 组专门断言这一点，防止「可选」被误实现成「全部可解」。

### 3.2 「所有已知问题清零」的执行结果

两轮合计记录在案的 25 项已知问题，第三轮 11 个提交全部清完（清单见 ROADMAP §一·三）。其中三项值得单独说明：

1. **8.3 短名绕过（新发现的 P0）**：`C:\PROGRA~1` 归一化后不等于 `C:\Program Files`，位置保护和名字名单**双双失效**。这不是理论漏洞——任何拼短名的路径都能绕过整个护栏层。修法是在归一化之前先 `GetLongPathNameW` 展开。
2. **删除中断不还原（由真实事故暴露的 P1）**：`rm_tree_strict` 的策略是「先改名到 `.oc-deleting-*`，再 rmtree」。改名成功后进程被杀（或 rmtree 中途失败），原目录就**永久消失**，只剩一个陌生名字的暂存目录。这个缺陷在正常测试里永远测不出来——必须先真的触发一次中断。修法是写 `pending-deletes.json` 日志 + 启动时 `recover_pending_deletes` 自动改回。
3. **资源包 URL 导入的 SSRF（新发现的 P1）**：`/packs/import-url` 让用户填任意 URL 并服务端拉取，等于提供了一个「从本机打内网」的入口。修法：拒绝非 http/https、拒绝带账号密码的 URL、拒绝回环与链路本地地址、拒绝云元数据主机名；**刻意不禁私网**（局域网自建资源包是合理用法）。

### 3.3 质量体系的缺口已补上

第二轮指出的结构性缺口——「护栏语义零自动化覆盖」——已由 `tools/guard_matrix.py`（**37 项断言**）补齐，并接入 `tools/selfcheck.ps1` 作为第 6 道门禁。

设计上最关键的一条：**必须有双向断言**。只断言「该拒的拒了」，会把护栏写成「什么都不让删」也能全绿。所以矩阵分五组——A 必须拒 / B 必须放行（防误伤）/ C 仅显式可选 / D 显式也拒 / E 短名。

另一个教训更值钱：**初版矩阵是假绿的**。把 `USER_DATA_DIR_NAMES` 整个清空后，矩阵仍然 rc=0——因为 `C:\Users\<u>\Documents` 被**位置规则**独立拦下，名字规则实际上零覆盖。补了「临时目录下别处的 Documents」这个用例之后，缺陷注入验证（清空→rc=1，无条件放行→rc=1，恢复→rc=0）才真正有效。**门禁自己也要被验证。**

### 3.4 对「收敛维护」结论的最终确认

三轮下来结论没变，但依据更硬了：**这个项目的价值在护栏层和解释层，而护栏层的正确性只能靠对抗测试保证**。现在 37 项矩阵进了门禁，下一个 P0 不必再等「下一轮审计」才发现——这是三轮里最有长期价值的一项产出，比修掉任何单个 bug 都重要。

诚实评估：**纯「看哪里占空间 + 删缓存」场景，WizTree/TreeSize + 两行 PowerShell 可替代约 70–80%**；但「看懂 → 安心删 → 沉淀为自己的清理习惯（规则/聚合组/换算）」这条链路，同类没有等价物。O-Cleaner 的真实壁垒是**解释层与护栏层**，不是扫描速度。

## 三、创新性排序（真实亮点 → 风险）

1. **安全护栏体系**（check_deletable 保护链 + 服务端重识别 + 回收站配对清空 + junction 解析）——本次审计证明它仍有可加固空间，但方向与密度在同类个人工具中罕见；
2. **中文解释知识库 + 资源包生态**——「让普通人看懂每个目录」的正解，packs 可社区化；
3. **MFT 加速 + 原生回退双引擎**——借力不捆绑，合规处理到位；
4. **单文件零依赖**——分发与审计成本极低；
5. **AI 只建议不删除**的边界设计——把 LLM 放进「顾问」位而非「执行」位，是正确的安全范式。
- 同质化风险：低（护栏与知识库无法被扫描器顺手复刻）；抄袭风险：中低（核心在断言库与知识库内容，均为持续劳动密集型资产）。

## 四、定位（一句话）

**它是「个人向空间治理台」，当前形态不适合也无需按可分发产品运营**——公开源码 + Releases 分发即可；若未来想推广，增量投入应全部落在「知识库/资源包内容」与「跨设备实测」（doctor.py 已备）上，而不是新功能。
